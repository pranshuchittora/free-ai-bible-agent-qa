# Maintain a directory people return to

## Repository setup

The local checkout cannot set GitHub repository settings. On GitHub:

- Set a clear description and the GitHub Pages directory URL as the website.
- Add relevant topics such as `free-ai`, `ai-api`, `llm`, `awesome-list`, `local-ai`, `rag` and `open-source`. Use topics that describe actual content.
- Confirm Pages publishes from the intended branch/root. Open `catalog.html` after deployment.
- Add labels: `good first issue`, `help wanted`, `verification`, `translation`, `template`, `accessibility`, `arabic`.
- Turn the most useful tasks in [GOOD_FIRST_ISSUES.md](GOOD_FIRST_ISSUES.md) into separate issues. Do not mass-create placeholders.
- Upload a readable social preview image showing the directory and its purpose. Avoid invented counts, results or badges.

## A practical two-week cycle

1. Recheck a small group of cloud entries using official sources. Prioritize user reports and the oldest review dates.
2. Try one starter on a clean environment. Record OS, Python version and actual result.
3. Review contributions and explain requested changes. Respond within the time you can sustain; do not promise an SLA you cannot keep.
4. Publish a release only for meaningful changes. Link merged PRs, credit contributors and state what was actually checked.
5. Share one concrete finding or demo with the community it helps. Adapt the post and respect each community's promotion rules.

The scheduled workflow checks source URL availability and uploads a report. It does not refresh quotas, translations, review dates or releases automatically. A 403/429 needs manual inspection; it does not prove a broken service.

## Measure usefulness and discovery

Record a weekly snapshot of GitHub Traffic visitors, views and referring sources while the data remains available. Track new external contributors, useful issues, merged external PRs and response time alongside stars. Do not present a star target as a promised outcome.
